# PRD — AirGuard

**Продукт:** AirGuard— розумний монітор якості повітря
**Версія PRD:** 1.0
**Автор:** QA Embedded (DZ-12)
**Статус:** Утверджено для проектування HIL-стенда

---

## 1. Загальний опис продукту та його призначення

**AirGuard** — настільний IoT-пристрій для моніторингу якості повітря в приміщенні(дім, офіс, і т.п.).

**Призначення:** давати користувачеві в реальному часі знати, чи є поточне середовище безпечним для дихання:
- вимірювати концентрацію CO2, температуру (°C) та відносну вологість (%RH);
- сигналізувати про погане повітря світлодіодом і звуковим сигналом (тривога при CO2 > порогу);
- публікувати показники у JSON через MQTT, щоб значення бачив мобільний застосунок / веб-дашборд;
- налаштовуватися користувачем (поріг тривоги, період вимірювання, топік MQTT).

**Проблема, яку вирішує продукт:** високий CO2 (>1000 ppm) — причина втоми, головного болю
та поганої концентрації. Користувач буде знати, коли провітрити кімнату, і мати історію
показників у застосунку, не думаючи про сам пристрій.

**Сценарій використання:**
пристрій увімкнено в розетку -> підключається до домашнього WiFi -> кожні 30 с вимірює
CO2/температуру/вологість -> публікує JSON у MQTT -> застосунок/борда малює графіки;
якщо CO2 перевищив поріг -> LED червоний + buzzer, а у застосунку push "Час провітрити".

## 2. Технічний стек

### 2.1. Hardware

| Компонент | Модель | Інтерфейс | Роль |
|---|---|---|---|
| Мікроконтролер | ESP32-S3 DevKitC-1 (N16R8) | - | DUT: обчислення, WiFi, MQTT-клієнт |
| Сенсор CO2 | MQ-135 (аналоговий) | ADC (GPIO4) | Вимірювання CO2-еквівалента 400–5000 ppm |
| Сенсор температури/вологості | SHT31 | I2C (GPIO8=SDA, GPIO9=SCL) | Температура +/-0.5 °C, вологість +/-3 %RH |
| Індикація стану | RGB LED | GPIO (GPIO2=R, GPIO3=G, GPIO10=B) | Кольорове кодування якості повітря |
| Тривога | Buzzer (active) | GPIO (GPIO11) | Звуковий сигнал при тривозі |
| Живлення | 5V USB / 3.3V ESP | - | Базове живлення |

### 2.2. Firmware(згенерована за допомогою ШІ)

За основу логіки для прошивки була взята прошивка fw_3 з попереднього ДЗ і трохи доопрацьована для поточного дивайсу
| Компонент | Технологія |
|---|---|
| Фреймворк | ESP-IDF v6.x (FreeRTOS) |
| Мова | C (C++) |
| WiFi/MQTT | esp-mqtt (QoS 1) |
| Збереження конфігу | NVS (Non-Volatile Storage) |
| OTA | esp_https_ota |
| Watchdog | task watchdog + RTC WDT |

### 2.3. Критичні аспекти для тестування

- **CLI через UART 115200 8N1** — командний інтерфейс для QA та сервісної налагоди:
  `help`, `status`, `config get/set <key> <value>`, `config save`, `factory_reset`,
  `calibrate co2 <fresh-air>`, `reboot`, `version`, `sensor <co2|temp|humi>`.
- **JSON-контракт MQTT-повідомлення** — фіксована схема payload.
- **Мультизадачність**: задача сенсора (читання ADC/I2C) і задача MQTT (команди конфігу)
  одночасно працюють з NVS/буферами
- **MQTT-клієнт у постійному циклі connect/publish** — потенційне місце memory leak.

## 3. Функціональні вимоги

### 3.1. Вимірювання та сенсори

- **FR-001 — Вимірювання CO2.** Пристрій вимірює концентрацію CO2-еквівалента в діапазоні
  400–5000 ppm з періодом 30 с (налаштовується, 5–300 с). Точність: ±50 ppm при
  калібруванні на свіже повітря (400 ppm). Аналоговий сигнал сенсора (0–3.3 В) лінійно
  мапиться у діапазон ppm.
- **FR-002 — Вимірювання температури та вологості.** Пристрій вимірює температуру в
  діапазоні 0…+50 °C з точністю +/-0.5 °C та відносну вологість 20–80 %RH з точністю +/-3 %RH через SHT31 (I2C).
- **FR-003 — CLI-інтерфейс.** Пристрій надає CLI через UART 115200 8N1 з командами:
  `help`, `status`, `version`, `reboot`, `config get/set/save`, `factory_reset`,
  `calibrate`, `sensor`. Кожна команда повертає відповідь не пізніше ніж за 500 мс.
  Після boot у лог друкується версія прошивки у форматі `v<MAJOR>.<MINOR>.<PATCH>`.

### 3.2. Конфігурація

- **FR-004 — Налаштування та збереження конфігу.** Користувач змінює параметри через CLI
  `config set <key> <value>`; зміни застосовуються без перезавантаження. Команда
  `config save` зберігає конфіг у NVS; після перезавантаження значення відновлюються.
  Ключі: `alarm_threshold_ppm` (400–5000), `measure_period_s` (5–300), `mqtt_topic`,
  `mqtt_broker_url`, `hysteresis_ppm` (50–500).
- **FR-005 — Валідація конфігу.** Команда `config set` відхиляє значення поза діапазоном
  (відповідь з помилкою, значення не змінюється). Невідомий ключ відхиляється.
- **FR-006 — Factory reset.** Команда `factory_reset` скидає всі параметри до заводських
  значень і перезавантажує пристрій.

### 3.3. Тривога

- **FR-007 — Тригер тривоги вище порогу.** Якщо значення CO2 > `alarm_threshold_ppm` (default 1000 ppm), пристрій переходить у стан `alarm=triggered`: RGB LED червоний, buzzer подає періодичні сигнали, поле `alarm` у `status` і в MQTT-payload стає `triggered`.
- **FR-008 — Скидання тривоги.** Пристрій виходить із тривоги (`alarm=idle`,
  LED зелений, buzzer вимкнено) лише коли CO2 падає нижче
  `threshold − hysteresis_ppm` (default 100 ppm). Це запобігає «блиманню» тривоги на межі порогу.
- **FR-009 — Калібрування CO2.** Команда `calibrate co2 <fresh_air>` калібрує аналоговий
  сенсор: поточна напруга мапиться у 400 ppm (свіже повітря). Калібрування зберігається у NVS.

### 3.4. Мережа та MQTT

- **FR-010 — WiFi-підключення.** Пристрій підключається до WiFi 2.4 ГГц за прописаними
  credentials, друкує отриманий IP у boot-лог, індикація LED відображає стан мережі
  (blink зелений — пошук, горить зелений — підключено). При втраті WiFi — автоматичний реконект.
- **FR-011 — MQTT-публікація.** Пристрій підключається до MQTT-брокера і кожен цикл вимірювання публікує JSON-payload у топік з конфігу.

  Приклад Payload:
  ```json
  {
    "co2_ppm": 850,
    "temp_c": 23.4,
    "humi_rh": 45.0,
    "alarm": "idle",
    "device_id": "airguard-01",
    "fw": "1.2.0",
    "ts": 1726000000
  }
  ```
- **FR-012 — MQTT-реконект.** При втраті зв'язку з брокером пристрій автоматично
  перепідключається і відновлює публікацію після відновлення брокера.

### 3.5. Оновлення та надійність

- **FR-013 — OTA-оновлення.** Пристрій приймає OTA-оновлення прошивки з HTTP-сервера
  (команда `ota <url>` через CLI або MQTT-команда). Після OTA версія у boot-лог і `version` відповідає новій, конфіг користувача зберігається.
- **FR-014 — Watchdog.** При зависанні будь-якої критичної задачі (сенсор/MQTT/CLI) watchdog перезавантажує пристрій; пристрій відновлює роботу після такого перезавантаження.

## 4. Нефункціональні вимоги

### 4.1. Продуктивність

- **NFR-001 — Boot time.** Час від подачі живлення до готовності CLI (рядок «App started»
  у boot-лог) ≤ 5 с при типовій конфігурації.
- **NFR-002 — Latency MQTT.** Затримка між моментом вимірювання і
  появою відповідного повідомлення у підписника брокера ≤ 2 с.
- **NFR-003 — Відгук CLI.** Час відповіді на будь-яку CLI-команду ≤ 500 мс.

### 4.2. Стабільність та надійність

- **NFR-004 — Відсутність memory leak.** `free_heap` за 8 годин безперервного прогону
  знижується не більш ніж на 5 КБ (допуск на природні коливання heap).
- **NFR-005 — Стійкість до power cycle.** 1000 циклів «config set → швидкий power cycle»
  без втрати конфігу (відсутність race condition у записі NVS).
- **NFR-006 — Відновлення після втрати брокера.** Пристрій відновлює MQTT-підключення
  ≤ 10 с після появи брокера і не перезавантажується через відсутність брокера.
- **NFR-007 — Автовідновлення після збою живлення.** Пристрій коректно завантажується
  після 1000 power cycle (без NVS-пошкоджень, конфіг на місці, reset reason коректний).

### 4.3. Сумісність та умови експлуатації

- **NFR-008 — Живлення.** Робота від USB 5 В ±5 %; струм споживання ≤ 300 мА
  (пік при WiFi TX ≤ 500 мА).
- **NFR-009 — Температурний діапазон.** Коректна робота при 0…+50 °C;
  поза діапазоном — вимірювання позначаються як невалідні, пристрій не ламається.
- **NFR-010 — Трасованість версій.** Версія прошивки друкується у boot-лог і в полі `fw`
  MQTT-payload та відповідає формату semver `v<MAJOR>.<MINOR>.<PATCH>`;

## 5. Критичні сценарії використання


### CS-1. Тривога при високому CO2 (безпека користувача)
Дитяча кімната, ніч. CO2 зростав до 1500 ppm — пристрій МАЄ подати тривогу (LED+buzzer+MQTT).
**Ризик:** користувач не провітриває кімнату, продукт втрачає сенс.
**Покриття:** FR-007, FR-008, NFR-002 → E2E-тест «CO2 → тривога → MQTT» (signal injection 1500 ppm).

### CS-2. Конфіг не зникає після ребуту (довіра до пристрою)
Користувач налаштував поріг 800 ppm і перезавантажив пристрій (перебій живлення).
**Ризик:** «рандомно зникає налаштування» — найчастіші проблеми IoT-юзерів.
**Покриття:** FR-004, NFR-005, NFR-007 → race-тест 1000 циклів rapid reboot.

### CS-3. Дані доходять до застосунку (обіцянка «дивись показники з телефону»)
Весь ланцюжок: вимірювання → JSON → WiFi → брокер → застосунок.
**Ризик:** юзер бачить порожній дашборд — найчастіша причина повернути пристрій
**Покриття:** FR-010…FR-012, NFR-002 → E2E-тест перехоплення payload MQTT-підписником.

### CS-4. OTA без «окирпичення» (оновлення в полі)
Тисячі пристроїв у користувачів отримують OTA. Один невдалий апдейт = масові повернення.
**Ризик:** пристрій не завантажується - кирпич
**Покриття:** FR-013 → OTA-тест на стенді + перевірка конфігу після OTA.

### CS-5. Місяць без догляду (пасивна надійність)
Пристрій працює 24/7 у домі користувача; «тихий» memory leak = «рандомні рестарти»
**Ризик:** репутація продукту, повернення, погані відгуки.
**Покриття:** NFR-004, FR-014 → 8-годинний leak-тест з графіком heap.
